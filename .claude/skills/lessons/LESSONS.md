# 失敗の記録

起きたことだけを書く。一般論は書かない。
1件は4行。場面は「次から」を差し込むときの索引になるので、短い名詞で書く。
新しいものを上に足す。

## 2026-09-26 long-dev が周ごとに時刻の起床で待っていた
場面: long-dev、スキル
起きたこと: AdaptiveAIStudio の long-dev が PR をマージするたびに「次の作業選びは 20:30」と見回りを予約して返答を終え、周の間が 30分〜2時間空いた。同じ時間に NetVision は続けて回っていた
判定の誤り: 「起床を予約せずに返答を終えない」だけを書き、「作業が残っているなら予約せずに続ける」を書かなかった。予約すれば終えてよいと読める
次から: 待ってよいのは走っているものの完了だけと書く。作業が残っていれば同じ返答で次の周へ。回転は2つのリポジトリのコミット間隔で比べて見る

## 2026-09-25 long-dev に auto-dev の止まる条件をそのまま継がせた
場面: long-dev、スキル
起きたこと: AdaptiveAIStudio の long-dev が PR のマージ可否など3つを利用者に聞いて止まり、翌日の Routine まで何もしなかった。Routine 用に E=23h を毎回書かせてもいた
判定の誤り: 期限のある auto-dev の「当たったら止まる」を、終わりの無い long-dev にそのまま使った
次から: long-dev は条件に当たった件だけを脇に置き、判断待ちに書いて次の作業へ進む。期限は付けない。止まるのは利用者が止めろと言ったときだけ

## 2026-09-24 結びつけ先を見ずに、動く Routine を止めて作り直した
場面: Routine
起きたこと: AdaptiveAIStudio の Routine 4つを「古い作り方だから動かない」と無効にし、新しいセッションに結びつけて作り直した。実際は利用者が AdaptiveAIStudio を開いて long-dev を回していたセッションに結びついていて、そのまま動くものだった
判定の誤り: `persistent_session_id` の先のセッションが何を開いているかを `get_session` で見ずに、作り方の名前だけで判定した
次から: Routine を止める前に結びつけ先の `session_context.sources` を見る。対象リポジトリがあれば止めない

## 2026-09-24 手元のツールの制約を Routine の仕様だと書いた
場面: Routine、スキル、ツール
起きたこと: `create_trigger` にリポジトリの引数が無いのを「新しいセッションは空になる仕様」と書き、「自分自身に結びつける」を正解にした。公式は Routine をプロンプト・リポジトリ・connector の3点セットと定義していた。`create_session` に `source_url` があり、それに結びつければ通った
判定の誤り: 使っているツールが公式の作成画面と同じ項目を持つか確かめず、ツールの欠けを設計だと思った
次から: 動かないときは公式の定義を先に読み、手元のツール一覧と突き合わせる。欠けている引数があれば、別のツールで補う経路を試してから「できない」と書く

## 2026-09-24 Routine を「毎回新しいセッションで」と書いた
場面: Routine、スキル
起きたこと: 新しいセッションで起こした Routine は sources と mcp_servers が空で、clone も push もできなかった。AdaptiveAIStudio で止まり、Daikenja で再現した
判定の誤り: トークンを減らすために「新しいセッション」を勧め、起きた環境に何が付くかを確かめなかった
次から: Routine は自分自身に結びつける。仕組みの説明は、この環境で1回起こして観測してから書く

## 2026-09-23 設計を勝手に縮めた

## 2026-10 long-dev を会話中のセッションに結びつけて起こし、空のセッションで終わった
場面: Routine、long-dev
起きたこと: long-dev の Routine を、利用者と話している最中のセッションに結びつけたまま fire_trigger で起こした。結びつけ先が動いていたため、Routine はリポジトリの無い新しいセッションを作り、30 秒で何もせず終わった。status は成功のままで、利用者に失敗を指摘された
判定の誤り: 「結びつけ先にリポジトリがあるか」だけを見て、「結びつけ先が動いている最中か」を見なかった。直すときも、利用者が長期開発に使っているこのセッションを外し、別のセッションを作った（利用者に「ここが長期じゃないの?」と言われた）
次から: long-dev はリポジトリの長期開発のセッション（題名に「長期開発」）で回す。別のセッションを作らない。そのセッションが作業中なら fire_trigger で起こさず、その場で auto-dev を始める。起こしたら、リポジトリにブランチかコミットが増えたのを見てから報告する

## 2026-10 完成絵でデザインの一致を優先し、ポーズの無い硬い絵にした
場面: 絵、完成絵、見せる前
起きたこと: 「キャラデザを使って絵を完成させて」に対し、デザイン画と同じ水着・同じ人物を保つことを優先して、設定資料の気をつけの立ち姿を切り抜いて背景に貼った。前に描いたポーズ付きの人物を使わず、「なんでポージングしてたキャラクターじゃないの」「芸術に関してはお前の方が間違ってる」と言われた
判定の誤り: 頼まれていない基準（デザインとの一致）を自分で足し、絵として整っているか・魅力があるかより上に置いた
次から: 絵の良し悪しは利用者の基準に従う。完成絵は、矛盾やあり得ない形が無く、絵として整っていて魅力があることを見る。前の周で良かった要素（ポーズ、構図）は捨てずに引き継ぐ。自分で基準を足すときは、先に利用者に1文で確かめる

## 絵の手本を「AI の見分け方」にした（2026-10-10）
- 場面: 絵、手本選び、見せる前
- 起きたこと: 「AI っぽくない絵を勉強して」で、AI の見分け方の解説を手本にし、AI の特徴を消す道具を作った。線と塗りを崩しただけの下手な絵になった
- 判定の誤り: AI っぽさを減らすことを、人の絵の良さに近づくことと取り違えた
- 次から: 絵の質の手本は、上手い描き手が意図して決めていること（光源、視線の誘導、材質、線の強弱、配色、構図）から取る。見分け方の解説は手本にしない
