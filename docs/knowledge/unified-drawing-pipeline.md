# 統一描画パイプライン設計

> 状態: 設計レビュー前。これは実装完了を意味しない。既存経路を調査して作成した移行設計であり、既定動作はこの文書だけでは変更しない。

## 1. 目的と非目標

### 目的

- 依頼の解釈から保存までを、1つの追跡可能な描画ジョブとして扱う。
- どのモデル・工程・パラメータが、どの画像を入力にして何を出力したかを再現できるようにする。
- 形・構図・色・線・質感を、根拠のない後処理や再描画で壊さない。
- 不具合のある工程だけを再実行し、合格済みの工程・画像を不用意に作り直さない。
- 「検品できなかった」を「合格」と扱わず、未確認・失敗・警告・合格を区別する。
- 品質、所要時間、メモリ使用量を同じ評価セットで比較し、改善を目視でも確認する。

### 非目標

- すべての絵を12工程に分割すること。
- すべてのモデルに pose/depth/line ControlNet や inpaint を強制すること。
- すべての画像に自動修正・自動美化を掛けること。
- 指標の点数だけで絵の良し悪しを決めること。
- 一度の変更で既存の全描画モードを置き換えること。

## 2. 現状監査で確認した構造上の問題

現行コードには、同じ「絵を描く」目的に対して複数の独立した経路がある。

1. `chatdraw.engine.Studio._draw`
   - `favmodels.precise(...)`、`way == "auto"`、base/reference の有無などで経路を振り分ける。
   - 条件を満たすと `chatdraw.omakase`、満たさない短い単独モデル依頼は直接 `Painter.paint` に進む。
2. `chatdraw.omakase.Omakase.run`
   - モデル選定、構図生成、hires、検品、部位修正、再検品を独自に制御する。
   - `hires` はモデル世代によって縮小→拡大→img2img、またはネイティブ解像度の一発描画に分岐する。
3. `chatdraw.phases.draw`
   - 12工程の別オーケストレーター。サムネイル、アタリ、体形検品、下描き、服・髪、線、下塗り、光、影、ハイライト、仕上げを別の状態機械で実行する。
   - 工程の中には実際に描かず計測だけをするもの、画像処理だけのもの、モデルで再描画するものが混在する。
4. `tools/gen/pipeline.py`
   - base/draw/face/hands/check の5工程を持つ独立実験経路。アプリの通常描画オーケストレーターとは別実装。
5. `chatdraw.twostage`
   - 構図モデルと仕上げモデルを別プロセス相当で扱う独立経路。
6. `chatdraw.finishers` / `chatdraw.postfx` / `chatdraw.upscale`
   - 生成後の加工・拡大は別の入口と品質判定を持つ。

このため、利用者が同じ「描く」を選んでも、依頼内容・設定・モデル能力によって通る工程、検品、再描画、保存情報が異なる。設計文書にも5工程・12工程・2段階・手描き工程案が併存し、研究案と実際の既定経路が混同されやすい。

また、既存の工程研究には重要な実測がある。工程分割が一発描画より5〜6倍遅くなった比較、線画の描き直しで霞み・枠・服の変化が発生した比較、下塗りで元の形や光が失われた比較が記録されている。したがって「人間の工程を模倣するために段数を増やす」こと自体を品質改善とみなしてはならない。

## 3. 統一後の責務分割

描画の入口は1つにし、モデルごとの差は Strategy/Adapter に閉じ込める。

- **RequestCompiler**: 利用者の依頼、禁止事項、参照画像、キャンバス、スタイル、既存レイヤーを正規化する。元の依頼文は変更せず保存する。
- **Planner**: 依頼とモデル能力・メモリ予算から工程計画を作る。計画と実行結果を分離する。能力不足の工程は「未対応」と明示し、別工程で代用したふりをしない。
- **StageRunner**: 共通の工程契約に従って工程を実行する。モデル呼び出し、画像処理、検品を個別の実装に委譲する。
- **QualityEvaluator**: 読み取り可能性、構造、依頼内容、画質、変更範囲を別々に評価する。検品器の例外・モデル未取得・信頼度不足は unknown とする。
- **RevisionPlanner**: 検出された問題と工程責任表から、最小範囲の修正を提案する。修正対象が特定できない場合は全体再描画を自動実行しない。
- **ArtifactStore**: 元画像、各工程画像、マスク、プロンプト、モデル・設定、検品結果、差分、ログを一意のジョブIDで保存する。
- **CanvasPublisher**: 全工程の確定後にのみキャンバスへ新規レイヤーとして公開する。失敗・キャンセル時に既存キャンバスを破壊しない。

`Studio._draw` は分岐先ごとに描画を完結させず、共通の `DrawingJob` を作って `DrawingOrchestrator.run(job)` を呼ぶ入口にする。旧経路は段階移行中の adapter として残す。

## 4. 標準工程モデル

全ジョブは次の論理ステージを持つ。実行するかどうかは Planner が決め、必ず状態を記録する。

| ID | 工程 | 役割 | 実行条件 | 完了条件 |
|---|---|---|---|---|
| S0 | Request | 依頼・制約・参照・出力条件の固定 | 常に | 入力が正規化され、元依頼が保存される |
| S1 | Plan | 構図・モデル・解像度・能力・予算の決定 | 常に | 計画と選定理由が記録される |
| S2 | Composition | 人数、画面配置、ポーズ、シルエット | 常に（単一モデルの一発描画もこの役割を兼ねる） | 構図候補または一発描画が保存され、採用理由が残る |
| S3 | Structure | 骨格・奥行き・パース等のガイド作成 | 信頼できる入力/対応モデルがある場合のみ | ガイドの信頼度と採否が記録される |
| S4 | BaseRender | 主画像をネイティブ推奨解像度で生成 | 常に | ベース画像とモデル設定が保存される |
| S5 | TargetedRevision | 顔・手・足・服・小物など問題箇所だけを修正 | 問題が検出され、局所化でき、モデルが対応する場合のみ | 修正前後の検品で対象問題が改善し、保護領域が不変 |
| S6 | StyleAndDetail | 線・塗り・光・質感・ディテールの調整 | 依頼または利用者の明示選択がある場合のみ | 変更の意図と品質差分が確認される |
| S7 | Upscale | 解像度拡大 | 最終解像度がベースより大きい場合のみ。原則として大きな再描画より先に行わない | 拡大後に線・顔・局所ディテールを再検品 |
| S8 | Finishing | ノイズ・色にじみ等の非生成画像処理 | 明示選択または明確な品質問題があり、効果が検証された場合のみ | 変化量、線保持、局所損傷を検査し、悪化時は元画像へ戻す |
| S9 | FinalQC | 全体・局所・依頼適合・画像破損・出力条件の確認 | 常に | pass / warning / fail / unknown のいずれかを記録 |
| S10 | Publish | レイヤー・ファイル・メタデータの確定 | FinalQC後 | 原画像を保持し、完成版を別成果物として公開 |

「スキップ」は成功ではない。理由を持つ `skipped` とし、`unsupported`、`not_needed`、`disabled_by_user` を区別する。

## 5. 工程の共通データ契約

すべての Stage は同じ入力・出力形式を持つ。

```python
@dataclass
class StageInput:
    job_id: str
    stage_id: str
    source_artifact: str | None
    prompt: str
    negative_prompt: str
    seed: int
    canvas_size: tuple[int, int]
    mask_artifact: str | None
    model_spec: dict
    parameters: dict
    constraints: dict

@dataclass
class StageResult:
    status: Literal["passed", "warning", "failed", "skipped", "unknown", "cancelled"]
    output_artifact: str | None
    mask_artifact: str | None
    metrics: dict
    issues: list[dict]
    elapsed_ms: int
    memory_peak_mb: int | None
    reason: str
    provenance: dict
```

- 入力画像は不変。工程は新しい成果物を作る。
- 同じ job/stage/入力hash/設定/seed は再現可能なキーを持つ。
- モデル・重みのrevision、sampler、steps、guidance、strength、scheduler、dtype、解像度を記録する。
- 失敗した工程の出力を次工程へ暗黙に渡さない。
- 検品の読み取り失敗は `unknown`。未検査を合格に変換しない。
- 画像の外側・マスク外は、局所修正ならピクセル完全一致を既定要件とする。境界ぼかしを使う場合はその幅を明示する。
- すべての変更は元画像との差分、変更率、領域別差分を残す。

## 6. 品質判定の原則

品質を単一スコアにまとめない。少なくとも次を独立に記録する。

1. **依頼適合**: 人数、対象物、衣装、色、ポーズ、背景、画角。
2. **構造**: 人体キーポイント、骨長比、関節、手足の重複、シルエット、パース。
3. **描画品質**: 線の連続性・太さ、エッジ、ぼけ、色にじみ、ノイズ、ディテール。
4. **同一性/保持**: 顔、髪色、目色、衣装、元画像の意図しない変化。
5. **局所安全性**: マスク外の不変、修正境界の継ぎ目、局所損傷。
6. **技術健全性**: 解像度、色モード、アルファ、破損、NaN、空画像。

各検品値には `readable`、`confidence`、`version`、`reason` を付ける。信頼度の低い自動検品は警告であり、機械的な再描画の根拠にしない。

自動修正は次の全条件を満たす場合だけ実行する。
- 問題が検出器で読めている。
- 問題箇所を十分な余白付きで局所化できる。
- 修正対象と保護対象を分離できる。
- 修正後に同じ検品と別系統の回帰検査を実行できる。
- 悪化した場合に元画像へ完全に戻せる。

## 7. モデル能力の宣言

モデルごとに能力を宣言する。能力名だけでなく、実際に使う条件と検証済み範囲を持つ。

- `text_to_image`
- `image_to_image`
- `inpaint`
- `control_pose`
- `control_depth`
- `control_line`
- `native_resolution`
- `max_resolution`
- `supported_aspect_ratios`
- `recommended_steps/guidance/sampler`
- `memory_estimate`

能力がない工程はスキップ理由を記録する。未対応の模型に無理な工程を通して、形が変わったり処理が失敗したりする設計を避ける。

## 8. 修正・再試行の制御

- 再試行は全体回数ではなく、工程ごとの予算を持つ。
- 同じ入力・同じパラメータ・同じseedの再実行を禁止し、再試行理由と変更点を必ず記録する。
- 失敗原因に応じて戻り先を固定する（構図→S2、骨格→S3/S4、局所部位→S5、色/線/質感→S6/S8）。
- 局所修正が悪化したらその成果物だけを破棄し、直前の合格成果物を維持する。
- 全体再描画は、構図・シルエット等の全体問題で、かつ利用者が許可した場合に限定する。
- 上限到達時は未解決項目を明示して停止する。「合格するまで無制限に回す」ことはしない。

## 9. 標準の利用者体験

- 進捗は「現在の工程 / 全工程」と工程名を表示し、モデル内部のstep進捗と混同しない。
- 各工程の状態（完了/警告/スキップ/失敗/未確認）を表示する。
- 生成中のプレビューは仮成果物として表示し、確定画像と区別する。
- 完成時は採用したモデル、解像度、工程、警告、修正履歴を参照できる。
- 元画像と完成画像を並べて比較できる。自動処理で元画像を上書きしない。
- 停止時は直近の安全な成果物から再開できる。

## 10. 検証戦略

### 固定評価セット

同じ依頼・同じseed・同じモデルrevision・同じ解像度の画像を固定し、次を含める。
- 全身、顔アップ、複数人、複雑な手、交差した腕、長い髪、細い装飾、複雑な服。
- アニメ塗り、厚塗り、線画重視、柔らかい塗り。
- 参照画像あり/なし、背景あり/なし、透過あり/なし。
- 正常画像と、検品器が誤検出しやすい画像。

### 必須の比較

- 旧経路 vs 統一オーケストレーター。
- 1工程ずつの画像と最終画像。
- 変更率、SSIM/LPIPS等、線保持、局所損傷、依頼適合、処理時間、ピークメモリ。
- 自動指標だけでなく、人が見たA/B判定。合成画像のテストだけで実画像品質を合格にしない。

### 合格条件

- 元画像より明確に悪い工程が最終画像へ残らない。
- 局所修正のマスク外が完全一致する。
- 検品不能を合格にしない。
- キャンセル・例外・メモリ不足でも既存キャンバスを壊さない。
- 同じ入力条件で再現でき、工程ごとの採否理由を追跡できる。
- 速度とメモリが旧経路より大幅に悪化する場合は、品質上の根拠がない限り既定にしない。

## 11. 段階移行計画

### A. 観測可能性を先に統一
- 既存の Omakase / phases / twostage / direct render の入出力を共通 StageResult に記録する。
- 画像hash、prompt、モデルrevision、設定、検品結果を共通形式で保存する。
- この段階では画像処理の挙動を変えない。

### B. 既存経路を共通オーケストレーターへ接続
- まず direct render を BaseRender adapter にする。
- 次に Omakase の選定・hires・検品・局所修正を adapter 化する。
- twostage と phases は同じ Stage 契約を使うようにし、独立した保存・検品の意味をなくす。
- 旧経路と新経路を同じ評価セットで比較する。

### C. 重複・矛盾する工程を整理
- 12工程のうち、実描画・画像処理・計測だけの工程を明確に分離する。
- 実画像の品質改善が証明できない工程は既定から外す。
- `tools/gen/pipeline.py` は研究ベンチとして残すか、アプリの共通Stageを使う実験runnerへ移す。アプリ本番経路と誤認させない。

### D. 描画品質の順で改善
1. 依頼の正規化とprompt/model設定の回帰。
2. 構図・人体・シルエットのベース生成。
3. 顔・手・足など局所修正。
4. 線・塗り・光・質感のスタイル工程。
5. 拡大・仕上げ・保存。
各工程で前後画像を見てから次へ進む。

### E. 既定切替
- 旧経路と同等以上の目視品質、局所保持、再現性、安定性が確認できた機能から切り替える。
- 旧経路は比較期間を経てから削除する。ユーザーの許可なく main にマージしない。

## 12. 先に実施する調査・実装タスク

1. `Studio._draw` の全分岐をテストで列挙し、どの依頼・設定がどの経路に入るかを可視化。
2. `Omakase.run/hires/fix_region/finish` の実際の入力・出力・検品・保存を追跡。
3. `phases.draw` の全12工程について、描画/画像処理/計測/スキップを分類し、実際に使われる条件を記録。
4. `twostage.run_stages` と `tools/gen/pipeline.py` の本番利用/研究利用の境界を明確化。
5. キャンバスへ公開する直前の保存・レイヤー処理を追跡し、失敗時の原画像保持を検証。
6. 固定評価セットで各経路の現状を採点し、品質低下の大きい経路から修正する。

**この設計をレビューし、段階Aの観測可能性統一を先に実装する。設計文書を追加しただけで描画品質が改善したとは判定しない。**
